# Ticket 14 查源：JT/T 808—2019 的 0x0200 报警标志

**结论：** 已从交通运输部在线阅读器逐行核对表 25。GNSS 模块故障、天线未接或被剪断、天线短路分别是 **bit 4、5、6**；它们与终端超速（bit 1）、疲劳驾驶（bit 2）一样，维持到报警条件解除。**紧急报警（bit 0）不同：由报警开关触发，收到应答后清零；清零不证明险情解除。** 2021 年第 1 号修改单不改这些位或处置说明。以下是查源结果，不是实现或测试通过记录。

## 1. 查哪一个字段

下文页码均写作「印刷页 / PDF 页」，PDF 页以封面为第 1 页。[交通运输部正文在线阅读][reader]中，§8.21「位置信息汇报」（20 / 24）给出消息 ID `0x0200`，要求发生报警时立即上报位置并附加报警状态。§8.21.1 表 23（21 / 25）给出两个不同的 `DWORD`：

- 起始字节 **0** 的「报警标志」查**表 25**（22 / 26）。下表按 `DWORD` 数值的 bit 编号，掩码由 `1 << bit` 换算，不是报文的字节偏移。
- 起始字节 **4** 的「状态」查**表 24**（21 / 25）。该字段 bit 1 是「0：未定位；1：定位」，bit 18–21 分别表示是否使用 GPS、北斗、GLONASS、Galileo 卫星定位。**未定位或未用某星座，均不能代替 GNSS 硬件故障位。**

## 2. 位号、原文和清位条件

出处：§8.21.1 表 25「报警预警标志位定义」，印刷第 22 页 / PDF 第 26 页（[官方阅读器][reader]；[同页版式副本][table25]）。「定义」列摘录置 1 的含义；「处理说明」列保留表内用词。

| bit | 掩码 | 定义 | 处理说明 |
|---:|---|---|---|
| 0 | `0x00000001` | 紧急报警，触动报警开关后触发 | 收到应答后清零 |
| 1 | `0x00000002` | 超速报警 | 标志维持至报警条件解除 |
| 2 | `0x00000004` | 疲劳驾驶报警 | 标志维持至报警条件解除 |
| 4 | `0x00000010` | GNSS 模块发生故障报警 | 标志维持至报警条件解除 |
| 5 | `0x00000020` | GNSS 天线未接或被剪断报警 | 标志维持至报警条件解除 |
| 6 | `0x00000040` | GNSS 天线短路报警 | 标志维持至报警条件解除 |

bit 5 是**一个位、两种可能原因**，不能据此区分未接与剪断。bit 13、14 是「超速预警」「疲劳驾驶预警」，不是 bit 1、2 的报警；bit 18「当天累计驾驶超时报警」也不等于 bit 2。表 25 全表按**处理说明原文**可复核为：

| 处理说明 | bit |
|---|---|
| 收到应答后清零 | 0、20、21、22、27、28 |
| 标志维持至报警条件解除 | 1–12、15–19、23–26、29 |
| 标志维持至预警条件解除 | 13、14、30 |
| 保留，无处置定义 | 31 |

这里按「处理说明」归类，不按名称猜测。例如 bit 16 名为「胎压预警」，原表处理说明写的是「标志维持至**报警**条件解除」。分类供核查，不表示项目支持所有位。

## 3. “条件解除”“收到应答”和“人工确认”不是同一件事

- **持续位如何撤销。** §7.3.4「终端报警」（7 / 11）规定由终端判断报警条件并在位置汇报中置位。对于维持至条件解除的报警，条件解除后应「立即发送位置信息汇报消息，清除相应的报警标志」。所以连续收到 bit 4 为 1，是终端反复报告同一标志仍在；之后按时序收到清掉该位的实时汇报，才是终端报告该条件已解除。没有下一份报告、连接断开或平台回了 ACK，都不等于终端报告解除。bit 1、2、5、6 同理。[正文 §7.3.4][sec734]、[表 25][table25]
- **紧急报警是触发后待应答清位，不是条件解除位。** 下一份 `0x0200` 的 bit 0 为 0，不能推出司机脱险、已维修或平台人员完成处置。“事件”在此只描述这种语义，不是说它只上报一帧，也不是一个新的消息 ID。表 25 对 bit 0 只写「收到应答后清零」，没有指定唯一的应答消息或结果码。[表 25][table25]
- **应答与人工确认各有字段。** §7.3.4 说平台**可**回复平台通用应答处理报警；§8.2（9–10 / 13–14）及表 5 中，`0x8001` 带应答流水号、应答 ID 和结果，`0` 是「成功/确认」，`4` 是「报警处理确认」。另见 §8.25（25–26 / 29–30）、表 35、36：`0x8203` 是人工确认报警消息，按报警消息流水号和人工确认报警类型指明对象；表 36 的 bit 0 是「确认紧急报警」，bit 1–2、4–19 在**这张表**中为保留。不能照搬表 25 作为表 36 的确认掩码，也不能把普通成功 ACK 或标志清零当成人工处置完成。[表 5][table5]、[表 35–36][table36]

**对 ticket 14 的边界：** 上述六个位的协议语义已有出处；从 `0x0200` 读到的应归为终端报告（`TERMINAL`），而非平台判定（`PLATFORM`）。这是来源映射，不是标准规定的平台事件模型。标准没有在这些条表中规定本项目的去重键、人工工单何时关闭，或让平台用紧急位降为 0 自动生成 `RECOVERED`。本次未改映射、未跑测试，不据此勾选实现验收项。

## 4. 第 1 号修改单逐项核对

[交通运输部公告第 66 号][notice]落款 **2021-11-04**，公开日期 **2021-11-10**。已读取公告链接的[附件 2 原始 DOC][amend]全文（附件 1 是 JT/T 794—2019，不是本标准）。该 DOC 按修改项编号定位，不以本地排版页码为准；全文只有两项：

1. 第 1 项新增 §8.65「卫星状态参数」，消息 ID **`0x0205`**，由终端每 **600 s** 上传。新增表 88、89；表 88 最后的「位置基本信息」为 `BYTE[28]`，描述为「数据格式按表23」。这是新消息**引用**原有位置基本信息，并非改写表 23、24 或 25。
2. 第 2 项在附录 B 表 B.1 增加序号 **76**「卫星状态参数」`0x0205`。

因此，第 1 号修改单**未改变** `0x0200` 的报警位号、表 25 的清位条件、§7.3.4 或人工确认消息。不能把卫星数量或每 600 s 的卫星状态报告解释为新增 GNSS 故障位或恢复条件。此结论限于 **2019 正文 + 该修改单**，不外推至后续修订、其他版本或厂商扩展。
